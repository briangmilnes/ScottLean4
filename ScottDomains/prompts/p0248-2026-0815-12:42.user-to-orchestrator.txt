`funSpace : (P : TokenPoset) → (Q : JoinTokens) → DInfinityFoundations (TokenIdeal (funTokens P Q))`. Built on §5.6 rather than topologically: give the *tokens* of [D → E] and let `idealDomain` discharge D1–D4. A token is a finite list of step functions `(a,b)`, ordered by entailment — **b is below every upper bound of what the other list contributes at a**. That phrasing says `b ⊑ ⊔{b' | (a',b') ∈ m, a' ⊑ a}` without having to assert the join exists, which is what keeps the definition first-order and join-free.

**Two limits, stated rather than glossed:**

1. The **value** side must carry total binary joins. For a general value domain a finite set of step functions is a token only when *consistent*, consistency is not decidable from a bare `TokenPoset`, so the carrier would be a subtype with an undecidable predicate and `enum` could not be constructed without choice — which this development still does not admit. Carrying joins as data removes the condition. §4's dualizing object **[D → 𝕊] is covered**; `sierpTokens` supplies `or`.
2. **Not proved**: that these ideals biject with the Scott-continuous maps D → E. That is the information-systems *definition* of the function space; identifying it with actual functions needs a notion of continuous map the D1–D4 vocabulary does not carry.

**Two interface weakenings to `TokenPoset` were required, and both are findings, not conveniences:**

- **Antisymmetry is never used** by `idealDomain` — a preorder suffices. This matters concretely: step-function tokens genuinely are only preordered, since `[(a,b)]` and `[(a,b),(a,b)]` entail each other without being equal. Demanding antisymmetry would have forced a quotient for no gain.
- **`enum_onto` needs only mutual entailment**, not equality, because ↑t depends solely on t's ⊑-class and ideals are down-closed. A bit-mask enumeration cannot reproduce a list's order or duplicates, so exact surjectivity was unattainable as well as unnecessary.
